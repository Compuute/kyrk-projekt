# Member Portal

A static, mobile-first, bilingual (Swedish + Amharic) Progressive Web App (PWA) for church members.

---

## Architecture & Design Principles

This portal was designed with three core constraints: **maximum performance**, **absolute privacy** (zero tracking, zero cookies), and **maintenance simplicity** for a multi-church setup. 

To achieve this, we chose the following architecture:

### 1. Static Site Generation (Eleventy / 11ty)
Rather than using a heavy client-side framework (like React or Vue) or a server-side engine (like PHP), the site is built as a static site using **Eleventy**.
* **Rationale:** Static files are served instantly from Cloudflare Edge CDNs, have zero runtime server costs, are virtually unhackable, and have perfect Lighthouse performance scores.
* **Templating:** Eleventy processes `.njk` (Nunjucks) templates located in `src/pages/` using a global shared layout `src/_includes/base.njk`. The output is compiled to the `dist/` directory.

### 2. Multi-Church Dynamic Configs (Modular Runtime Content)
The member portal is a single codebase that serves multiple different churches dynamically.
* **How it works:** 
  1. The selected church ID is stored in the browser's `localStorage` (default is `nacka`).
  2. At runtime, `app.js` fetches the church list from `churches.json` and the specific content configuration from `churches/{id}/content.json`.
  3. The page title, footer (org number, phone, name), and schedule events are dynamically populated based on this configuration.
* **Benefit:** Onboarding a new church requires zero code changes. You only need to add their details to `churches.json` and upload their content folder under `churches/{id}/content.json`.

### 3. Client-Side Bilingual Toggle (Swedish & Amharic)
* **DOM Structure:** Every bilingual element contains two children: one with class `sv` and one with class `am` (e.g. `<span class="sv">Hem</span><span class="am">መነሻ</span>`).
* **Logic:** When the user clicks a language pill (Swedish/Amharic), `app.js` runs `applyLanguage(lang)` which toggles `display: none` on the opposing language class.
* **Benefit:** Language switching is instantaneous with zero page reload, providing a premium native-app feel.

### 4. Zero-Dependency Vanilla Testing
To keep the codebase maintainable and fast:
* All unit and integration tests under `tests/` are written using vanilla Node.js assertions (`require('assert')` and `fs`).
* They require **zero external dependencies** (no Mocha, Jest, or npm installs needed), meaning tests run in milliseconds and never break due to package deprecations.
* Running `make test` triggers the Eleventy build and runs all Node assertions sequentially, as well as the Python backend suites.

## Directory Structure

```
frontend/member-portal/
├── dist/                 # Compiled static site (gitignored, generated by 11ty)
├── src/
│   ├── _includes/
│   │   └── base.njk      # Global HTML shell (header, footer, PWA register)
│   └── pages/            # Eleventy page templates (.njk)
├── tests/                # Vanilla Node.js test suite
├── app.js                # Core JS logic (localization, church switching, SW register)
├── styles.css            # Responsive, mobile-first styling system
├── sw.js                 # PWA Service Worker (offline network-first caching)
├── manifest.json         # PWA Manifest (metadata for home screen installation)
└── churches.json         # Master list of supported churches
```

## Development Workflow

### 1. Build the Site
To compile the templates and copy assets to `dist/`, run:
```bash
npx @11ty/eleventy
```

### 2. Run Local Development Server
Use your preferred static server to serve the `dist/` directory, or run the top-level make target to test the entire project.

### 3. Run Test Suite
To run all frontend tests:
```bash
cd frontend/member-portal
for t in tests/test_*.js; do node "$t"; done
```
Or run the full pipeline test target from the project root:
```bash
make test
```
